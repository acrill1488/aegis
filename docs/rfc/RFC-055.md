# RFC-055: GreenBoost Integration Protocol (GBIP)

## Status

Implemented as the stable AEGIS client boundary for GreenBoost.

## Decision

AEGIS is a client of GreenBoost and does not vendor its scheduler, resource
manager, telemetry, discovery, or runtime. Network interaction is centralized
in `GreenBoostClient` (and its async equivalent), using the existing HTTPX and
Pydantic dependencies.

The client exposes `discover`, `snapshot`, `reserve`, `heartbeat`, `release`,
`cancel`, and `health`. Requests and responses are converted to the canonical
`NodeReference`, `ResourceRequest`, `ResourceReservation`, and
`ResourceSnapshot` contracts. HTTPX exceptions never cross the boundary.

Read-only calls may use the configured bounded retry policy. Reservation and
release calls are never automatically retried because their server-side result
may be ambiguous. Every operation has explicit connect, read, write, and pool
timeouts.

Configuration is read from the central services configuration under
`greenboost` (`enabled`, `base_url`, `api_key`, timeout values, and `retries`).
`AEGIS_GREENBOOST_BASE_URL` and `AEGIS_GREENBOOST_API_KEY` are supported by the
same resolver. Secrets and Authorization headers are never included in errors
or logs.

When GBIP is disabled, the existing OCR-focused GreenBoost adapter retains its
legacy behavior. Enabling GBIP makes its snapshot path use `GreenBoostClient`;
this preserves existing runtime APIs while providing an explicit migration
gate.

Diagnostic commands are `aegis greenboost health`, `discover`, and `snapshot`.

## Upstream compatibility

The reviewed upstream `main` branch currently documents GB-Synapse, MCP, and a
metrics health endpoint, but does not publish the reservation REST surface
described by this RFC. Consequently, GBIP keeps all endpoint knowledge inside
the client and transport. Live reservation acceptance requires a GreenBoost
deployment implementing the RFC-055 `/v1` service contract.
